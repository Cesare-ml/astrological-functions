# Chaldean planetary hours — isolated experimental facts (F5)

Status: **IMPLEMENTED_ISOLATED**. The code in `src/planetary-hours.mjs` is a standalone direct-file ESM experiment, **not** a package export or a production calculation service. It contains no astronomical algorithm, Swiss dependency, timezone database, private customer data, interpretation, or claims of causal efficacy.

## Contract

```js
import { buildPlanetaryHours } from '../src/planetary-hours.mjs';
const schedule = buildPlanetaryHours({
  availability: 'AVAILABLE',
  weekday: 'SUNDAY', // caller-asserted LOCAL CIVIL weekday at sunrise
  sunriseUtc: '2026-11-15T06:00:00Z',
  sunsetUtc: '2026-11-15T18:00:00Z',
  nextSunriseUtc: '2026-11-16T06:00:00Z',
});
// schedule.hours: 24 immutable facts (12 DAY, 12 NIGHT)
// hour #1 = SUN; #2 = VENUS; next day's first hour starts with MOON
```

The **caller** must provide three actual, ordered, reliable UTC solar events: today's sunrise, today's sunset, and next sunrise, with the intended observer and sunrise/sunset model already decided. `weekday` is the **local civil calendar weekday at the first sunrise**, not the weekday of the UTC ISO date; this library neither guesses the location/timezone nor checks an asserted weekday against astronomy. Sun events across UTC date boundaries are valid. Each day/night interval must be positive and shorter than 24 hours. Events with a segment too short to form twelve non-empty millisecond intervals are rejected.

Hours are generated by dividing sunrise→sunset into 12 consecutive equal-duration **day** portions and sunset→next sunrise into 12 consecutive equal-duration **night** portions. Durations are unequal between day and night except on equal-length days. Boundaries are partitioned using integer milliseconds and include no overlap or gaps; each interval is `[startUtc, endUtc)` and exact sunset enters the first **night** hour. The very last end boundary is the next sunrise, not included. Returned instants use canonical ISO UTC with three fractional digits; all returned objects/arrays are frozen.

The traditional sequence used here is `SATURN → JUPITER → MARS → SUN → VENUS → MERCURY → MOON` repeating, with the first hour of Sunday `SUN`, Monday `MOON`, Tuesday `MARS`, Wednesday `MERCURY`, Thursday `JUPITER`, Friday `VENUS`, Saturday `SATURN`. Each subsequent hour advances one position. No interpretation is performed.

For unavailable sunrise/sunset events, explicitly call:

```js
const unavailable = buildPlanetaryHours({
  availability: 'UNAVAILABLE',
  weekday: 'FRIDAY',
  reason: 'POLAR_DAY', // or POLAR_NIGHT / SUN_EVENTS_UNAVAILABLE
});
// unavailable.hours is an empty frozen array; no fabricated times
```

Outputs use `PlanetaryHoursSchedule / 0.1.0-experimental` and `sunEventsEvidence: CALLER_SUPPLIED_NOT_ASTRONOMICALLY_VERIFIED`. A consumer MUST NOT treat this claim as authenticated ephemeris provenance: the function cannot check where the supplied times came from. For a trustworthy schedule, the future pinned VirgoStars Ephemeris provider must return observer-specific sunrise/sunset (horizon altitude, refraction, elevation, atmosphere and timescale stated), date/timezone chosen by the consuming application, precision/capability and polar handling; the adapter must verify those before calling this pure scheduler. Do not infer events from JPL SPK vectors alone without an independently validated rise/set solver.

## Exact-instant lookup (F5 extension)

`lookupPlanetaryHour({ schedule, instantUtc })` resolves a **caller-selected** instant against the complete sunrise-to-next-sunrise `buildPlanetaryHours` schedule. It never reads the device clock, guesses a timezone, computes solar positions, or extrapolates the next day's hours.

```js
import { buildPlanetaryHours, lookupPlanetaryHour } from '../src/planetary-hours.mjs';

const schedule = buildPlanetaryHours({
  availability: 'AVAILABLE', weekday: 'SUNDAY',
  sunriseUtc: '2026-11-15T06:00:00Z',
  sunsetUtc: '2026-11-15T18:00:00Z',
  nextSunriseUtc: '2026-11-16T06:00:00Z',
});
const lookup = lookupPlanetaryHour({
  schedule, instantUtc: '2026-11-15T18:00:00Z',
});
// FOUND: hour 13 (NIGHT), JUPITER, elapsedMs = 0
```

The result is a frozen, discriminated `PlanetaryHourLookup / 0.1.0-experimental` fact:

- `FOUND`: a frozen canonical `hour`, plus non-negative integer `elapsedMs` and strictly positive integer `remainingMs`.
- `OUTSIDE_SCHEDULE`: `hour: null` for times before sunrise or at/after next sunrise. No rollover or implicit regeneration.
- `UNAVAILABLE`: `hour: null` and the original polar/solar unavailability `reason`.

All branches include normalized `instantUtc` and the **caller-supplied, not astronomically verified** evidence label. Sunrise and every planetary-hour start are inclusive; each end is exclusive. Sunset enters hour 13. A JSON-deserialized schedule is accepted if it exactly matches fresh canonical facts, regardless of object-key order. Inconsistent or altered schedule facts are rejected as `INVALID_SCHEDULE`. The check is **structural only**: it does not establish the authenticity of the original sunrise/sunset input or its weekday. Users of untrusted inputs must independently validate event provenance and observer data.

## Hardened schedule validation — 12 November 2026

The exact-instant lookup verifies the **whole** schedule, not just the queried hour. In addition to rejecting changed rulership, times and metadata, it rejects a sparse `hours` array (JavaScript `Array.prototype.every` otherwise skips holes), an inherited rather than owned `hours` property, and extra enumerable properties on the array. A plain JSON serialization round-trip remains supported. This is a structural integrity check, **not** a signature or a verification of the provider's astronomical accuracy.
